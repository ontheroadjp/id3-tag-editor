# MP3タグ自動取得・比較編集Webアプリケーションの設計検討

## 1. 目的と背景

### ユーザーの要求・決定

Ubuntu上のMP3ファイルについて、インターネットからタグ情報を取得し、タグを編集・保存する仕組みがほしい。

MP3の状態は混在している。

- タグがほぼ空のファイル
- タグが一部のみ入力されたファイル
- 誤ったタグが入力されたファイル
- 正しいタグが入力されたファイル
- 曲名・アーティスト名がわかるファイル名
- `track01.mp3` や `unknown.mp3` など識別に使いにくいファイル名

最初はCLIスクリプトとして相談したが、最終的に**Webアプリケーション**とする方針に変更した。理由は、音声再生と既存タグ・取得タグの視覚的比較、フィールド単位の反映選択を行いたいため。

ユーザーが明示的に指定した操作フロー：

1. ファイル一覧を表示する。
2. ファイルをクリックする。
3. 右側画面の上部にアートワークと再生プレーヤーを表示する。
4. 右側画面の下部右側に既存タグ情報を表示する。
5. 下部左側には当初「タグ情報取得」ボタンを表示する。
6. ボタンを押すとオンラインから情報を取得する。
7. ボタンの位置に取得タグを表示する。
8. 取得タグ（左）と既存タグ（右）をフィールドごとに1対1で対応させ、中央に `→` を表示する。
9. 反映したくない項目は `→` をクリックして `×` に切り替える。
10. 「タグ情報を反映」ボタンで選択した項目のみMP3へ書き込む。

画面構成について、ユーザーは**B：左右分割型**を明示的に選択した。左側にファイル一覧を常時表示し、右側で再生・タグ編集を行う。A：一覧と編集画面の切り替え型は選択しなかった。

### 想定環境・制約（会話内の設計前提）

- Ubuntuで実行する個人利用アプリ。
- Docker Composeによる起動を想定。
- PCブラウザでの利用が中心。
- MP3を初期対象とし、将来のFLAC等への拡張余地は残す。
- 既存のファイル名・ディレクトリ構成を変更しない。
- LAN内利用を想定するが、公開方法・認証は未確定。
- タグの取得とファイルへの書き込みを分離する。
- 一括自動更新よりも、ユーザーが確認して反映する操作を優先する。

これらの一部はAIの提案であり、すべてがユーザーによって個別承認されたわけではない。

## 2. 当初検討したCLI方式

### 音声指紋を利用する理由

ファイル名や既存タグが信用できない場合でも、音声からChromaprintでフィンガープリントを生成し、AcoustIDで楽曲を照合できる。

基本フロー：

```text
MP3ファイル
  ↓ 既存タグ・ファイル名を参照
Chromaprint（音響指紋生成）
  ↓
AcoustID（楽曲識別）
  ↓
MusicBrainz（メタデータ取得）
  ↓
mutagen（ID3タグの読み書き）
```

取得候補のタグ：

| タグ | 内容 |
|---|---|
| TITLE | 曲名 |
| ARTIST | アーティスト |
| ALBUM | アルバム |
| ALBUMARTIST | アルバムアーティスト |
| DATE | 発売年・日付 |
| TRACKNUMBER | トラック番号 |
| GENRE | ジャンル（取得可能な場合） |
| APIC | アルバムアート（別途取得） |

**制約：** 音響指紋で楽曲を特定できても、どのアルバム・再発盤・ベスト盤・ライブ盤の収録音源かまで一意に決まるとは限らない。したがってアルバム名、発売日、トラック番号、アートワークは候補選択が必要な場合がある。

### 既存OSS beets の検討

Python製CLI音楽ライブラリ管理ツール **beets** が候補となった。MusicBrainzとの照合、`chroma` プラグインによる音響指紋を利用できる。

会話で提示された導入例：

```bash
sudo apt install pipx libchromaprint-tools
pipx install beets
beet config -e
```

設定例：

```yaml
plugins: musicbrainz chroma

directory: ~/Music
library: ~/.config/beets/library.db

import:
  copy: no
  move: no
  write: yes
  autotag: yes
```

操作例：

```bash
beet import -t -C ~/Music/Test
```

- `-t`：候補確認を伴うインポート。
- `-C`：ファイルをコピーしない。
- `-s`：曲単位でインポート。
- `-q`：確認を省く静かなインポート。曖昧な候補はスキップする想定。

**注意：** これらは会話で提示された例であり、このチャットで実行検証したものではない。設定の詳細、バージョンごとの挙動は実装時に確認する。

beetsはライブラリへのインポートを中心とするため、既存タグを部分的に補完し、項目ごとに変更可否を選択するUIには必ずしも適合しない。Webアプリ化の決定後、beetsを中核とする案は採用されていない。

### 検討された自作CLIインターフェース

```bash
mp3tag ~/Music
mp3tag ~/Music --recursive
mp3tag ~/Music --dry-run
mp3tag ~/Music --overwrite
mp3tag ~/Music --cover
```

これは**提案されたインターフェース例**であり、実装済みスクリプトではない。Webアプリ化によって優先度が下がった。

当初の更新方針候補：

- A：空欄だけ補完し、既存値は上書きしない。
- B：空欄補完に加え、高確度で明らかな誤りを修正する。
- C：変更内容を確認してから更新する。

ユーザーはA/B/Cを明示選択していない。その後のWeb UI案は**Cに近い、項目単位の確認・選択方式**になった。

## 3. 最終的なUI設計

### 3.1 画面全体

ユーザー決定：**左右分割型（B）**。

AI提案の画面比率：

- 左側：25〜30%。ファイルブラウザ。
- 右側：70〜75%。上部にアートワーク・プレーヤー、下部にタグ比較・編集。

概念図：

```text
┌────────────────────────────────────────────────────────────────────┐
│ MP3 Tag Manager                                          Settings │
├──────────────────┬─────────────────────────────────────────────────┤
│ Music            │ [既存アートワーク]  選択中のMP3ファイル名       │
│ [検索...]        │                    曲名 / アーティスト          │
│                  │                    ▶ ───────── 0:00 / 2:18    │
│ 01 - xxx.mp3     ├─────────────────────────────────────────────────┤
│ 02 - yyy.mp3  ◀  │ タグ情報の比較              候補 1 / 3          │
│ track003.mp3     │                                                 │
│ unknown.mp3      │ 取得タグ          選択       既存タグ           │
│ 05 - zzz.mp3     │ TITLE: Help!       →        TITLE: Help        │
│                  │ ARTIST: Beatles   ×        ARTIST: ...        │
│                  │ ALBUM: Help!      →        ALBUM: 未設定       │
│                  │ DATE: 1965        →        DATE: 未設定        │
│                  │ TRACK: 1          ×        TRACK: 02          │
│                  │ GENRE: Rock       ×        GENRE: Pop         │
│                  │                                                 │
│                  │                    [選択したタグを反映]         │
└──────────────────┴─────────────────────────────────────────────────┘
```

画面モックに表示された「The Beatles」「Help!」「Yesterday」等は**説明用サンプル**であり、実際に取得されたデータではない。

### 3.2 左側：ファイルブラウザ

AI提案機能：

- ディレクトリ階層の展開・折りたたみ。
- ファイル名による検索・絞り込み。
- 未処理、確認済み、タグ未設定によるフィルタ。
- ファイルクリックで右側の内容を更新。
- 処理済みの視覚的表示。
- 前後ファイルへの移動。
- 大量ファイルを考慮し、ディレクトリ単位で一覧を取得する。

「処理済み」はアプリ内で確認・保存した履歴であり、**タグの正確性を保証する状態ではない**。

### 3.3 右上：プレーヤー

ファイルを選択すると、タグ取得前でも以下を表示する。

- MP3に埋め込まれた既存アートワーク。
- アートワークがない場合のプレースホルダー。
- ファイル名と既存の曲名・アーティスト等。
- 再生・一時停止。
- シークバー。
- 再生位置と総時間。
- 音量調整。
- 前後ファイルへの移動。

ブラウザでの途中再生・シークのため、音声配信APIはHTTP Rangeリクエストに対応する設計。

### 3.4 右下：タグ取得前

- 左：**「タグ情報を取得」ボタン**。
- 右：既存ID3タグ情報。

取得ボタンを押しただけではMP3ファイルは変更しない。

### 3.5 取得後：候補選択と比較

音響指紋を取得し、AcoustID、MusicBrainzで候補を取得する。

複数候補がある場合は、比較画面で採用する前に選択できるようにする。

候補の表示項目：

- アーティスト
- 曲名
- アルバム名
- 発売年
- トラック番号
- 必要に応じてアートワーク

候補を選択すると、下部左側に取得タグを表示し、右側の既存タグと対応させる。

**取得タグは左側で手動編集可能**にする案。例えば取得された `The Beatles` を `Beatles` に修正してから書き込める。

中央の選択アイコン：

- `→`：そのフィールドを反映する。
- `×`：そのフィールドを反映しない。
- クリックで相互切り替え。

AI提案の初期選択ルール：

| 条件 | 初期状態 |
|---|---|
| 既存が空欄、取得値あり | 反映 |
| 既存と取得値が同一 | 反映不要 |
| 既存と取得値が異なる | 原則反映しない |
| 取得値が空欄 | 反映しない |

これらは推奨仕様であり、最終実装前に詳細確定が必要。

### 3.6 アートワークの比較

取得画像と既存の埋め込み画像を並べて表示し、他のフィールド同様に反映・除外を選択する。

AI提案では、初期バージョンで更新するのはID3のフロントカバー（APIC type 3）のみとし、その他の画像を維持する。

画像取得先はCover Art Archiveを想定。音声認識だけでアルバムアートを確定させず、選択されたリリースに対応する画像を取得する。

## 4. メタデータ取得処理

提案された処理順序：

```text
ファイル選択
  ↓
既存タグ・アートワークの読み取り
  ↓
「タグ情報を取得」
  ↓
Chromaprint / fpcalc で音響指紋生成
  ↓
AcoustID で音声識別
  ↓
MusicBrainz で録音・リリース候補を取得
  ↓
候補選択（複数ある場合）
  ↓
Cover Art Archive で画像取得
  ↓
既存タグと比較・編集
  ↓
反映するフィールドを選択
  ↓
mutagen で選択フィールドのみ更新
  ↓
タグを再読み込みして確認
```

候補の曖昧さがあるため、取得情報を無条件に確定情報として扱わない。

AcoustIDの利用にはアプリケーション用APIキーが必要と説明された。MusicBrainzの通常の読み取りAPIはAPIキー不要と説明されたが、リクエスト頻度制限に注意する必要がある。会話では「1秒あたり1リクエスト以下」が目安として提示された。**実際の最新利用規約・制限は実装時に再確認する。**

ジャンル情報はMusicBrainzに必ず存在するわけではないため、欠損値は空欄として扱う。

## 5. アプリケーション構成

### 5.1 採用提案

フロントエンドとバックエンドは論理的に分離するが、**Dockerコンテナは1つ**とする案。

```text
Browser
   │
   ▼
FastAPI
   ├── Frontend (HTML / CSS / JS)
   ├── File Browser API
   ├── Audio Streaming API
   ├── Tag Read / Write API
   ├── Fingerprint Service
   │      └── Chromaprint (fpcalc)
   ├── Metadata Service
   │      ├── AcoustID
   │      ├── MusicBrainz
   │      └── Cover Art Archive
   └── SQLite
          ├── 処理履歴
          ├── タグ取得キャッシュ
          └── 確認済み状態

Host filesystem
   └── /music (MP3ファイル)
```

| 役割 | 技術 | 理由 |
|---|---|---|
| Web API | Python / FastAPI | Pythonで処理を統合 |
| Frontend | HTML / CSS / Vanilla JavaScript | ビルド工程・依存を最小化 |
| ID3操作 | mutagen | ID3フレーム単位で編集 |
| 音響指紋 | Chromaprint / fpcalc | 音声識別用の指紋生成 |
| 音声照合 | pyacoustid / AcoustID | 音響指紋を使った識別 |
| メタデータ | musicbrainzngs / MusicBrainz | 曲名・アルバム・リリース候補 |
| 画像 | Cover Art Archive | リリース画像 |
| DB | SQLite | 個人利用に十分な規模 |
| 配布・運用 | Docker Compose | 起動・更新を簡素化 |

初期段階ではReact、PostgreSQL、Redis、Celeryなどを導入しない方針が提案された。必要性が確認されるまで複雑さを増やさない。

外部API通信や指紋生成を伴うタグ取得は、UIをブロックしない**非同期ジョブ**として扱う。

### 5.2 API案

| Method | Endpoint | 役割 |
|---|---|---|
| GET | `/api/files` | ファイル一覧 |
| GET | `/api/files/{id}` | ファイル情報と既存タグ |
| GET | `/api/files/{id}/audio` | 音声ストリーミング |
| GET | `/api/files/{id}/artwork` | 既存埋め込み画像 |
| POST | `/api/files/{id}/lookup` | タグ取得ジョブ開始 |
| GET | `/api/lookups/{job_id}` | ジョブ進捗・候補 |
| GET | `/api/releases/{id}` | リリース詳細 |
| POST | `/api/files/{id}/tags` | 選択フィールドの書き込み |
| GET | `/api/files/{id}/history` | 更新履歴 |

`{id}` はクライアントから直接任意パスを渡すのではなく、サーバー管理のファイルIDを使う設計。実装時はIDから実パスを解決する際の許可ディレクトリ検証も必要。

タグ更新リクエスト例：

```json
{
  "expected_version": "file-version-token",
  "updates": {
    "title": "Yesterday",
    "artist": "The Beatles",
    "album": "Help!",
    "tracknumber": "13"
  }
}
```

反映しないフィールドは `updates` に含めない。

`expected_version` により、表示後に別プロセス等が変更したファイルへ誤って上書きすることを防ぐ設計。バージョントークンの生成方法は未決定。

```yaml

    build: .
```

- Tailscale経由での利用も候補。

## 6. ID3タグ書き込みとデータ保護

### 必要とされた安全策

- タグ取得だけではファイルを書き換えない。
- 音声データを再エンコードしない。
- ID3v2.3 / ID3v2.4を扱う。
- 反映対象として選択したフィールドのみ更新する。
- 未選択フィールド、未知のタグ、独自タグは極力維持する。
- 書き込み前に元のタグ情報をバックアップする。
- 書き込み後に再読み込みし、結果を検証する。
- 変更履歴を保持する。
- 書き込み失敗時の復旧方法を設計する。
- 読み込み後にファイルが変更されていれば競合として書き込みを拒否する。
- ファイルロック等で同時更新の競合を抑止する。

**技術上の注意：** mutagenでタグ全体を再構築すると独自タグが失われる可能性がある。選択したID3フレームのみを更新する必要がある。タグ書き込みは自動的に完全なトランザクションになるわけではないため、バックアップ・検証・復旧処理が重要。

バックアップについて、タグ情報だけの保存かファイル全体のバックアップか、復元操作の仕様・保持期間・容量管理は未確定。

## 7. 開発フェーズ

### Phase 1 — ファイル閲覧・再生

- ファイル一覧
- ディレクトリ移動
- 既存タグの表示
- 既存アートワークの表示
- MP3再生
- 読み取り専用での動作確認

### Phase 2 — タグ情報取得

- Chromaprint / AcoustID
- MusicBrainzから候補取得
- 複数候補の選択
- 取得結果の比較表示
- アートワーク候補の取得

### Phase 3 — タグ編集・反映

- フィールド単位の `→` / `×` 切り替え
- 取得値の手動編集
- 選択フィールドのみ書き込み
- アートワーク書き込み
- 変更履歴・復旧
- 書き込み後の検証

### Phase 4 — 操作性改善

- キーボードショートカット
- 検索・絞り込み
- 処理済み管理
- タグ取得キャッシュ
- 次のファイルへの自動移動

初期リリースの完成条件として提案された操作フロー：

```text
ファイル選択
  → 再生
  → タグ取得
  → 候補選択
  → 比較
  → フィールド単位で選択
  → 反映
```

AI提案の検証順序：

1. Phase 1でファイル閲覧・再生を安定させる。
2. 状態が異なるMP3を10〜20曲程度使い、Phase 2で識別精度と候補の品質を評価する。
3. Phase 3でデータ保全と部分更新を重点的にテストする。
4. Phase 4で大量ファイル処理の操作性を改善する。

## 12. 追加で決まった利用環境・制約

### ライブラリの規模と対象形式

- 音楽ライブラリ全体では **5,000曲以上**ある。
- 最初からライブラリ全体に固定の曲数上限を設けるより、ディレクトリ単位で必要な一覧を取得する方針とした。
- 当初は MP3 を初期対象としていたが、実機確認の際に M4A ファイルもあることが分かった。
- Phase 1・2 では **MP3 と M4A の閲覧・再生・タグ候補取得**を対象とした。
- Phase 3 のタグ書き込みについて、MP3 と M4A を同時に対象とするか、形式ごとに段階を分けるかは、実装前に安全性を含めて検討する。

### アクセス方法

- 初期段階では、アプリを実行する**同じ PC のブラウザからのみ**利用する。
- 将来的には外部からアクセスできるようにしたい。
- 外部公開に進む前に、認証・アクセス制御・HTTPS・公開方法を別途設計する。
- 現在のローカル限定構成を、そのまま外部公開してよいと決めたわけではない。

### 元ファイルの扱い

ユーザーが明示した制約：

- 音楽ファイルの**場所・ファイル名・ディレクトリ構成を変更しない**。
- 音声を再エンコードしない。
- 情報取得とタグ書き込みを分離する。
- タグの書き込み前にバックアップするのは、**ファイル全体ではなくタグ情報のみ**とする。

タグ情報のバックアップについて、保存形式、未知のタグの扱い、復元操作、保持期間、容量管理は引き続き未決定。

## 14. Phase 2 で得られた UI・操作上の決定

実機で使いながら、最初の設計案から次のように調整した。

### 候補選択

国別盤・再発盤などが大量に一覧表示されると、選択するより入力したほうが早いほど使いにくかった。

そのため、候補の操作を次の**2段階**にした。

1. **アルバムを選択する。**
2. **そのアルバムの版を選択する。**

- アルバム候補は名前順に表示する。
- 表示領域は約5件分とし、それ以外はスクロールで確認する。
- アルバム名・アーティスト名で入力に応じて絞り込める。
- 同名アルバムの別の版を、一覧内の入れ子の折りたたみで大量表示する方式は、ユーザーから使いにくいとの指摘を受けて変更した。
- 版によって発売日・曲順・アートワークが異なる場合があるため、録音の識別結果だけで版を確定しない。

### 画面レイアウト

- 左にファイル一覧、右に選択中のファイルの操作画面を置く。
- 右側上部に既存アートワークとプレーヤーを置く。
- その下に、**全幅のタグ取得・候補選択ペイン**を置く。
- さらに下に、**取得情報を左、既存情報を右**として対応させた比較欄を置く。
- Phase 2 の UI は実機確認を通じて改善し、ユーザーからデザインが良くなったとの反応を得た。

### 言語

- ユーザーは、外国人アーティストの情報が日本語表記になる場合、英語のまま扱いたいと希望した。
- その後、取得情報の言語を選択できるようにした。
- 現在の言語選択は、**MusicBrainz に登録されているリリースの言語による候補の絞り込み**であり、テキストを自動翻訳する機能ではない。
- 言語未登録の版も確認できるようにした。
- 対象言語の版が登録されていない場合や、表記とリリース言語が必ずしも一致しない場合がある。

### トラック番号

ユーザーの既存タグが `4/17`、取得情報が `4` と表示されたため確認した。

- `4` は4曲目を表す。
- `4/17` は、そのディスクの全17曲中の4曲目を表す。
- **どちらも形式として有効**であり、総曲数の有無が異なる。
- 現在は、選択された版のディスク内総曲数を取得できる場合、`4/17` のように表示する。
- 総曲数や曲順は版・ディスクによって異なり得るため、異なる版の値を無条件に正しいものとして扱わない。

### フォルダ移動

「← 上のフォルダ」を押した際は、再生を止め、選択中の曲と取得結果をクリアし、メインペインを初期状態に戻すようにした。

## 15. 次の作業：Phase 3 の検討

次は、取得したタグを必要に応じて編集し、フィールドごとに反映可否を選び、ユーザーの明示的な操作で保存する Phase 3 を進めたい。

**ただし、まだ詳細仕様を確定していない。** 実装を始める前に、リポジトリの現状とこの文書を踏まえ、全体計画と不明点を提示し、ユーザーと順に決めること。

### 検討が必要な事項

1. **対象形式と対象フィールド**
   - MP3・M4A の両方を最初から書き込み対象とするか、形式ごとに段階を分けるか。
   - 曲名、アーティスト、アルバム、アルバムアーティスト、日付、トラック番号、ジャンル、アートワークのうち、初期対応する範囲。
   - 複数値、ディスク番号、コメント、歌詞、独自タグなどの扱い。

2. **比較・編集・初期選択**
   - 取得値の手動編集方法。
   - 既存値が空、取得値と同じ、取得値と異なる場合の初期状態。
   - ユーザーの当初の要望である、フィールド間の `→` / `×` と明示的な反映操作をどう実装するか。
   - 取得値が空欄の場合、意図的な値の削除を許すかどうか。

3. **タグ情報のみのバックアップと復元**
   - ID3 と M4A それぞれのタグ情報を、未知・独自の情報や画像も含めてどの形式で保存するか。
   - バックアップと対象ファイルをどう対応付けるか。
   - 復元 UI、復元対象、保持期間・容量管理。
   - ファイル全体のバックアップは行わない方針だが、タグのみで復元できる範囲と限界を検証する。

4. **書き込みの安全性**
   - 既存の ID3v2.3 / v2.4 や文字コードの扱い。
   - M4A のメタデータ構造とアートワークの扱い。
   - 未選択・未知・独自タグをどう維持し、何を検証できるか。
   - 比較表示後のファイル変更を検出する方法。
   - 同時更新の制御、書き込み失敗時の復旧、書き込み後の再読み込みと検証。
   - 音声部分を再エンコードせず、ファイル名・場所を変更しないことの確認。

5. **テストと導入**
   - 状態の異なるテスト用ファイルを使った検証。
   - 実際の音楽ライブラリに適用する前の確認方法。
   - 書き込み権限を与える範囲と、現在の読み取り専用マウントからの変更方法。

キーボードショートカット、処理済み管理、取得キャッシュ、次のファイルへの自動移動などは候補として残っているが、Phase 3 の安全な書き込みに必須かどうかを確認してから優先順位を決める。
